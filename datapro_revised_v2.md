# DataPro — Revised Architecture (v2)

> **Status:** This document is a working revision of `datapro.md` produced after spending hands-on time with Trino in `datapro/` (empty coordinator + dynamic catalogs) and earlier Postgres-backed experiments. It is more concrete and more opinionated than v1 because we now know what the substrate actually does for free, and what it doesn't. v1 remains as historical reference; new design work should build on this document.

---

## What changed from v1

- **Architecture is explicitly four-layered**, not "Core + Dashboard." The Core/Dashboard split still exists but it's a deployment decision; the four layers are the *conceptual* decomposition.
- **The data source model is now four sibling categories**: *native*, *stock*, *flex*, *bespoke*. Each describes a different mix of "who writes the code" and "what runtime path the source takes." There is no longer a separate "adapted" category — Python-with-just-in-time-materialization has been replaced by *flex*, in which AI-written Python runs *inside Trino* via a single DataPro-owned plugin.
- **The object model is cleaner**. Objects are mostly *namespaces*; the real semantic content lives in *traits* declared on each object type and populated per-catalog.
- **Concrete catalog-building UI proposed.** Three-panel layout. The AI's deliverable is a Python module that conforms to the flex contract. Fetch/transform survive as a useful mental model but are realized as the flex framework's `get_splits` / `read_split` callbacks. No background workers, no schedules — the flex framework calls Python on demand, query by query.
- Several v1 ideas have been downgraded or removed:
  - "Adversarial performance certification" — kept in spirit but not redesigned here.
  - Direct VictoriaMetrics-as-objects-via-Trino pattern — replaced by either flex (for moderate volumes) or bespoke (for large ones). (Note: VictoriaMetrics-as-time-series remains a first-class case, see Layer 3b.)
- **Time series remains a first-class primitive**, parallel to (not folded into) the object model. See Layer 3b.
- **The query surface is a deterministic, deliberately-restricted subset of SQL semantics**, not raw SQL. The exact syntax (JSON / SQL-flavored DSL / something else) is open, but it compiles 1:1 to Trino SQL and that compiled SQL is visible to the consumer. Results are nested typed objects, not row sets. See "The Query Surface."
- **Stock connectors stay Java; flex absorbs the long tail.** DataPro ships a curated library of pre-built, deeply-configurable Trino connectors (logs, CSV, JSONL, syslog, …) — *stock* — that are written once in Java by DataPro and configured per source. For everything else that doesn't need Java-grade hot-loop performance, *flex* is the answer: a single DataPro-owned Trino plugin that delegates every query callback to a per-catalog Python module, generated by AI. The 484-line Java SPI tax for one-off connectors that prompted this restructure (see `examples/log-connector/`) is paid exactly once — for the flex framework itself — instead of per source.
- **Bespoke connectors are now rare.** A genuinely one-off Java SPI plugin is reserved for cases where Python performance is unacceptable (extreme row volumes, latency-critical hot paths, exotic wire protocols). Phase 1 does not ship bespoke. AI generation of bespoke is deferred to Phase 2+, by which time we have real customer signal about which shapes truly need it, and AI can template off the stock library when applicable.
- **Core/Dashboard is now a concrete three-component deployment**, not a vague split. *DataPro Core* is the data plane: it owns the Trino deployment, has its own internal Postgres for metadata, implements all four conceptual layers, and exposes a Flask HTTP API that consumers (DataMCP, DataViz, programmatic clients) talk to. *DataPro AI* is the AI plane: a Flask backend that handles agent orchestration, LLM provider integration, and sandbox execution of AI-proposed code. *DataPro UI* is the presentation plane: a React single-page application served as static assets, with no backend of its own. The SPA calls both Core and AI directly. See "DataPro Core, AI, and UI."

## Vocabulary: Connector vs. Catalog

DataPro uses these two terms with the same strict distinction Trino does. Confusing them is the single easiest way to lose track of which layer something belongs to.

- **Connector** — *the how.* A plugin/implementation that knows how to read a class of backend. The Trino-built-in `postgresql` connector, the DataPro-shipped `logs` stock connector, the DataPro-shipped flex framework, a one-off bespoke Java plugin written for a single customer. Connectors are code, shipped as JARs, deployed into the Trino image (or, for non-Trino paths like TSDBs, into Core). One connector typically serves many catalogs.
- **Catalog** — *the what.* A named, configured instance that picks a connector and binds it to a specific backend with specific properties. `prod_orders` (a catalog using the `postgresql` connector pointing at the prod orders DB), `app_logs` (a catalog using the `logs` stock connector pointing at `/var/log/apps`), `deployment_xml` (a catalog using the flex connector pointing at a Python module). Catalogs are configuration, persisted in Core's Postgres, and managed via Core's HTTP API. Each registered data source in DataPro is a catalog.

The Trino-side mechanics mirror this: a Trino catalog is created with `CREATE CATALOG <name> USING <connector> WITH (...)`. DataPro Core's job is to keep Trino's actual catalogs converged to the desired set persisted in its Postgres.

The DataPro semantic layer that bolts on top (which object types this catalog advertises, trait mappings, proposed links, safety contract) is **not** a separate primitive in this document — it's part of the catalog's configuration. If we ever need a separate name for it (e.g. because one catalog can expose multiple semantic profiles), candidates are *Binding*, *ObjectSource*, or *Exposure*. For now: the catalog config carries both the Trino-level properties and the DataPro semantic metadata.

A consequence worth pinning: **"AI writes a connector" is rare**, and only applies to bespoke (Phase 2+). **"AI writes a catalog configuration"** is the common case — for native, stock, and flex, AI proposes config (YAML/JSON) and, for flex, a Python module that the existing flex connector loads. The shipped Java connector binary is reused across catalogs.

## The Four Layers

```
┌──────────────────────────────────────────────────────────────────┐
│  Layer 4 — Relationships (Links)                                 │
│  Named relationships between object types, with cardinality.     │
│  Operates on objects only. Time series sit outside this layer.   │
├────────────────────────────────────┬─────────────────────────────┤
│                                    │                             │
│  Layer 3a — Objects & Traits       │  Layer 3b — Time Series     │
│                                    │                             │
│  Typed namespaces (Application,    │  Named series with labels   │
│  Host, LogLine, …) with optional   │  (cpu_usage{host=h-918}).   │
│  traits (Identity, Temporal, …).   │  Time-bound, aggregated,    │
│  Multi-source backed.              │  schema-less. No traits.    │
│  Hot path goes through Trino.      │  Hot path bypasses Trino.   │
│                                    │                             │
├────────────────────────────────────┴─────────────────────────────┤
│  Layer 2 — Data Sources                                          │
│  Object sources: native / stock / flex / bespoke (via Trino).    │
│  Time-series sources: TSDB native protocol (bypass Trino).      │
│  Same backend may have both. AI-assisted setup; config + code    │
│  artifacts are the deliverable.                                  │
├──────────────────────────────────────────────────────────────────┤
│  Layer 1 — Trino                                                 │
│  Off-the-shelf federation engine. Used by object sources only.   │
│  Time series queries bypass Trino and talk directly to the       │
│  TSDB's native protocol (PromQL, InfluxQL, etc.).                │
└──────────────────────────────────────────────────────────────────┘
```

Each layer has a clean responsibility and a clean handoff to the layer below it. The 3a/3b split is the most important architectural decision in this document: **objects and time series are siblings, not subset/superset**. They have different access patterns, different runtimes, and different consumer-facing APIs.

A query enters at Layer 4 (link-traversal queries), Layer 3a (single-object or trait-based queries), or Layer 3b (time-series queries). Layer 4 and 3a queries descend through Layer 2 and resolve to Trino SQL at Layer 1. Layer 3b queries descend through Layer 2 and resolve directly to native time-series protocols (PromQL, InfluxQL, etc.) — Trino is not involved.

The rest of this document specifies each layer in detail, then walks through how a query of each kind traverses them.

## Layer 1 — Trino (the substrate we don't build)

We've validated this hands-on (see `datapro/`). Trino gives us:

- **Connector ecosystem** — ~40 connectors out of the box: Postgres, MySQL, Mongo, Iceberg, Delta, Hive, Kafka, Elasticsearch, etc. Each registered via a one-to-five-line `*.properties` file.
- **Federation** — single query can span any combination of catalogs. We confirmed this with `postgresql × tpch` JOINs.
- **Cost-based query planner** — dynamic filters, push-down, broadcast vs. shuffle joins. Pushdown is sensitive to statistics (we saw this with `ANALYZE`).
- **Distributed execution** — coordinator + workers, scale-out is configuration.
- **Introspection via `system` catalog** — `system.runtime.queries`, `system.runtime.nodes`, etc. Free Dashboard backing.

What Trino does not give us:

- Object identity across sources.
- Named relationships.
- Schema discovery for non-tabular data (XML, logs, free-text files).
- Safety contracts.
- Field-level provenance.
- A semantic query language.
- A reasonable execution model for time-series queries. Trino's row-oriented planner is the wrong shape for `range + aggregation + label filter` queries against a TSDB. Time-series workloads in DataPro bypass Trino entirely (Layer 3b).

Everything DataPro builds is in service of supplying those.

## Layer 2 — Data Sources

### Two kinds of data sources

DataPro distinguishes two fundamentally different kinds of data sources at this layer, mirroring the 3a/3b split above:

- **Object data sources** route through Trino. They expose typed objects to Layer 3a. They use the four-category model (native / stock / flex / bespoke) described below.
- **Time-series data sources** bypass Trino and talk to TSDB protocols directly. They expose time series to Layer 3b. They have their own (simpler) model, described after the object source section.

A single backend may be registered as **both** an object source and a time-series source — these are two independent registrations against one backend, serving two different access patterns. We lean on this in the dual-exposure pattern (Layer 3b).

### Object data sources: the four-category model

Every external dataset that should expose typed objects falls into one of four categories. The categories are siblings, not nested — they describe different combinations of "who writes the code" and "where that code runs."

| Category | Code lives in | AI generates | Per-source artifact | Runtime path |
| --- | --- | --- | --- | --- |
| Native | Trino itself | nothing | YAML config | Trino's built-in connector |
| Stock | DataPro-owned Trino plugin | nothing (config only) | YAML config | DataPro stock plugin |
| Flex | DataPro-owned flex plugin + per-source Python module | the Python module | Python module + YAML config | Flex plugin (Java) → Python subprocess (per catalog) |
| Bespoke | Per-source Trino plugin | a Java SPI plugin | a Trino plugin JAR | Hand-rolled connector |

The categories are checked in the order written. The earliest category that applies is the right answer.

#### 1. Native

The data is already in a system Trino has a built-in connector for, *and* the connector reads it as rows. Postgres tables, MySQL tables, MongoDB collections, Iceberg tables, Kafka topics with a registered Avro/JSON schema — all native.

**AI work:** None at the substrate level. AI may still do *configuration* work (which tables to expose, how to map them to object types, what links exist), but it does not write code.

**Runtime path:** Trino reads from the source via its existing JDBC/native connector. No DataPro-owned code in the hot path.

This is the cheap, ideal case. Most operational data in real deployments (e.g. customer Postgres) is native.

#### 2. Stock

DataPro ships a curated library of well-engineered, deeply-configurable Trino connectors for common data shapes Trino doesn't speak natively. The first members of this library:

- **`logs`** — directory tree of plain-text log files; per-file or per-line parsing via regex/delimited/json/logfmt/syslog modes; path-pattern templates that double as partition declarations.
- **`csv` / `jsonl`** — directory tree of CSV/TSV/NDJSON files with optional schema inference and explicit type overrides.
- **`syslog`** — RFC 5424 / RFC 3164 with built-in field extraction.
- **`http_paginated`** — REST APIs that paginate JSON, configured via URL templates, auth scheme, JSONPath for row extraction.

(More can be added as patterns repeat across customers.)

**AI work:** Propose the YAML configuration (path pattern, parser type, parser arguments, column declarations, partition columns, safety contract). No code is written. The connector binary itself is DataPro-owned, human-reviewed once, and deployed in every customer's Trino image.

**Runtime path:** Trino loads the stock connector binary and the per-source configuration. Trino reads via the connector at query time, in Java, with full pushdown / partition-pruning / parallel-splits behavior.

Stock is the right answer whenever the data shape matches one of the shipped connectors. It's the highest-leverage category — write once, configure forever.

#### 3. Flex

Flex is the *long tail* category. The data shape doesn't match any stock connector, but it doesn't need Java-grade per-row performance either. Customer-specific XML schemas, vendor REST APIs, weird file layouts, in-house event archives, occasionally-queried datasets — all flex.

**AI work:** Generate a single Python module that conforms to the **flex contract** (described in detail in § How flex works, below). The module exposes:

- `get_tables()` — declares table names, columns, types.
- `get_splits(table, predicate)` — enumerates units of work given a query's filter predicates. A "split" is anything: a file path, a URL, a chunk index. Trino dispatches splits across workers in parallel.
- `read_split(table, split, columns)` — yields rows for one split. Lazy, batched, streamable.

Fetch/transform survive as a *mental model*: `get_splits` is "find the work" (the fetch part — locating files, listing API pages, walking a Git repo); `read_split` is "turn this work into rows" (the transform part — parsing one file, mapping one API response to a row set). The flex framework calls them through the SPI; the user-supplied Python doesn't have to know what an SPI is.

**Runtime path:** When a query touches a flex catalog, Trino calls into the **DataPro flex plugin** (Java, baked into the Trino image). The flex plugin maintains a Python subprocess for each registered flex catalog and calls its `get_tables` / `get_splits` / `read_split` over an Arrow-Flight-style IPC protocol. Trino sees a normal connector — splits, predicates pushed down, rows produced as `Page`s. The Python is invisible to the planner.

The big architectural payoff: **adding a new flex catalog requires no Trino restart and no Java compile.** AI writes Python; Core registers a new catalog with `CREATE CATALOG flex_my_thing USING flex WITH ("flex.module_path" = "...")`; the flex plugin loads the Python module on first use; queries work. Compare this to bespoke, where every new catalog required building a new connector JAR and restarting Trino with a new plugin path.

Flex pays a real performance cost — Python row-iteration is 10-100× slower than Java for similar work, and there's an IPC boundary between Trino and Python. For most "long tail" sources where data volumes are modest and the bottleneck is I/O anyway, this is fine. For sources where it isn't — multi-terabyte hot tables, latency-critical real-time feeds — the right answer is to either:
1. **Promote the shape to stock**, if it generalizes to many customers (one PR to the stock library, a free upgrade for everyone).
2. **Drop to bespoke**, if it's genuinely one-of-a-kind and Java's per-row cost matters.

#### 4. Bespoke

A hand-rolled Java SPI plugin written for a single source. The data shape doesn't match any stock connector, doesn't generalize enough to warrant adding to stock, *and* Python performance via flex is unacceptable.

**AI work for bespoke:** AI generates a Trino SPI plugin in Java/Maven. **Critically, AI does not start from a blank page.** It picks the closest stock connector as a template — same Maven structure, same handle classes, same lifecycle methods, same safety-contract integration — and modifies the parts that genuinely differ (the metadata declaration, the splits enumeration, and the page source). Only when no stock connector is structurally similar does AI start from scratch against the raw SPI.

**Runtime path:** Same as stock. The bespoke plugin is deployed alongside DataPro, registered as a Trino plugin, and queried via Trino directly.

This is the heaviest category and the one where AI generation has the biggest safety surface. It should be **rare** — the proof-of-concept in `examples/log-connector/` was 484 lines of mostly-boilerplate Java for a four-column log table, and that's a lower bound. The decision to go bespoke is a judgment that *both* (a) no stock connector can be made flexible enough, *and* (b) flex's Python performance is insufficient. Both are uncommon individually; together they are rarer still.

Bespoke is **deferred past Phase 1.** Phase 1 does not ship AI generation of bespoke connectors. By the time we ship it (Phase 2+), we'll have real customer signal about which shapes actually need it, and the AI agent for it can template off the existing stock library.

#### Decision tree

```
New data source
       ↓
  Trino has a built-in connector AND data is tabular?
       ↓
   YES → NATIVE                       (no DataPro code, just config)
       ↓
       NO
       ↓
  A stock connector matches the shape?
       ↓
   YES → STOCK                        (config only; AI proposes YAML)
       ↓
       NO
       ↓
  Per-row Python performance acceptable?
       ↓
   YES → FLEX                         (AI writes a Python module;
                                       runs in Trino via the flex plugin;
                                       no Trino restart needed)
       ↓
       NO
       ↓
  → BESPOKE                           (AI writes a Java SPI plugin from
                                       the closest stock template; rare;
                                       Phase 2+)
```

Stock is checked before flex because stock gives Trino-grade Java performance for the same operator effort as flex (config only). Flex is checked before bespoke because Python "is enough" for the vast majority of long-tail sources, and avoiding Trino restarts is a large operational win. Bespoke is reserved for the genuine performance-critical edge.

The categorization is a *recommendation* by AI, reviewed by a human in the Dashboard. It is changeable later if assumptions about volume or hotness turn out wrong — a flex catalog that turns out too slow can be upgraded to bespoke; a frequently-recurring flex shape can be generalized into a new stock connector.

### How flex works (implementation sketch)

Flex is one **DataPro-owned Trino plugin** (Java, against the SPI) shipped in the HMS Trino image. Each flex-backed catalog points at a **per-source Python module** on disk (path stored in catalog properties and in Core's Postgres). The Java side owns all SPI boilerplate: metadata, splits, page sources, type marshalling, retained memory, error surfaces. Python implements only the data semantics.

**Process model.** The flex plugin runs a **long-lived Python worker subprocess per flex catalog** (not one interpreter per query — startup cost would dominate). The worker loads the configured module once, serves `get_tables` / `get_splits` / `read_split` calls for the lifetime of the catalog, and is torn down when the catalog is dropped or Trino restarts. Health checks restart a crashed worker.

**Java ↔ Python boundary.** Communication is **batch-oriented columnar IPC** (Apache Arrow Flight or an equivalent framing over gRPC or stdin/stdout). The Java side builds `Page`s from incoming Arrow record batches; backpressure is explicit so a slow Python reader cannot unbounded-buffer the coordinator. Predicate pushdown: Trino's constraint summary for the table scan is serialized into a Python-readable structure so `get_splits` can prune work before `read_split` runs.

**The Python contract (stable ABI).** The exact names and packaging are TBD, but the logical surface is:

| Callback | Responsibility |
| --- | --- |
| `get_tables()` | Return schema: logical table names, column names, Trino types. |
| `get_splits(table, constraints)` | Return an iterable of opaque split descriptors (dicts with a small fixed key set — e.g. file path, URL, offset range). Must be deterministic given constraints. |
| `read_split(table, split, columns)` | Yield batches of rows for that split only; may stream. |

Optional hooks (`init_catalog`, `shutdown`) can manage credentials or HTTP session reuse without violating "no background materialization jobs" — only **in-process** caching inside the worker between calls is allowed; nothing that implies scheduled refresh or cross-query durable cache unless we add it explicitly later.

**Sandboxing and limits.** The Python worker runs with **restricted filesystem, network, and CPU/memory caps** (same class of controls as DataPro AI's sandbox for draft code — see Open Questions). Flex code executes on the **Trino data plane** (where customer data is reachable), so the bar is higher than for AI-only sandboxes: flex modules are reviewed artifacts, versioned like catalog configs, not ad-hoc REPL output.

**Operational note.** New flex catalogs use `CREATE CATALOG` (dynamic catalog management) plus Core-persisted metadata — no Trino restart, no new JAR. Bespoke and stock still require image/plugin rollout on the Trino side when *DataPro's* shipped Java changes; only flex's *Python* changes are hot-swappable at catalog granularity.

### The catalog-building experience (the Dashboard view in DataPro UI)

This is the operator-facing UI that turns "I have a data source, please expose it" into a registered DataPro catalog. It lives inside the DataPro UI React SPA (see § DataPro Core and DataPro UI for the full deployment topology). It is the heart of Phase 1's user-facing work.

#### Three-panel layout

```
┌────────────────────────────┬───────────────────────────────────────┐
│                            │                                       │
│                            │  RAW DATA SOURCE                      │
│                            │  (e.g. directory listing of XML       │
│   AI CHAT                  │   files, snippet of one file,         │
│   (the catalog-building  │   table schema if SQL, etc.)          │
│    agent)                  │                                       │
│                            │                                       │
│                            ├───────────────────────────────────────┤
│                            │                                       │
│                            │  TABULAR PREVIEW                      │
│                            │  (sample rows the flex module would   │
│                            │   emit from `read_split` — first ~50, │
│                            │   column names and types)             │
│                            │                                       │
└────────────────────────────┴───────────────────────────────────────┘
```

The user converses with AI on the left. Top-right shows what AI is currently looking at as input. Bottom-right shows what AI proposes to output. The user iterates until the bottom-right looks right, then commits.

#### Two stages (mental model → flex callbacks)

The AI's job is still explained to operators as **two stages**, because that maps cleanly to how humans think about messy sources. Under the hood they compile to the flex contract (`get_splits` + `read_split`):

1. **Discover / enumerate ("fetch").** Locates units of work: files, API pages, Git paths, partition shards.
   - Implemented as **`get_splits(table, constraints)`** — returns split descriptors Trino can schedule in parallel across workers.
   - Examples: walk a directory tree for `*.xml`, list S3 prefixes, paginate a REST catalog endpoint.
   - No cross-query durable cache and no cron — each query gets a fresh split enumeration given the query's predicates (Trino may call this once per planning phase, not "every row").

2. **Parse / shape ("transform").** Turns one split's payload into typed rows.
   - Implemented as **`read_split(table, split, columns)`** — yields batches for that split only.
   - Examples: parse one XML file with XPath, regex one log file, map one JSON page to rows.

Each stage's code is rendered to the user separately and can be rerun and edited independently via the chat ("change column `started` to `started_at`, parse it as ISO-8601"). Separating enumeration from per-split parsing keeps failure attribution clean.

There is intentionally **no third stage** for environment setup or scheduling. Repo clones, auth, mounts — either live in `get_splits` / `read_split` or in small `init_catalog` hooks that set up the Python worker process, not a separate batch system.

> **Open question:** whether the UI should always show two code panels (`get_splits` vs `read_split`) or fuse them for tiny sources where a single function is clearer.

#### No background work, by design

Flex catalogs do not run as background workers, daemons, cron jobs, or scheduled materialization jobs. There is no "refresh every 15 minutes." There are no execution batches.

At query time, Trino's flex plugin **calls the Python worker** for split enumeration and then for each split's row batches. Rows stream through the IPC boundary into Trino `Page`s; **nothing is written to a separate materialization tier** (contrast with the old "adapted → `memory` connector" design). There is no cross-query cache by contract — each query sees splits enumerated under that query's predicates. (Within-query, Trino's own execution cache may apply; that's Trino's concern, not a DataPro batch layer.)

This removes worker fleets, schedules, stale-cache semantics, and "the materialization job wedged" failure modes. The price is **per-query work in Python** plus IPC overhead — acceptable for the long tail; unacceptable cases move to **stock** (if the shape generalizes) or **bespoke** (if Java hot-loop performance is required).

#### Catalog configuration is the artifact

The output of the catalog-building flow is **declarative configuration plus reviewable code** where the category requires it. The configuration says:

- What category (`native` / `stock` / `flex` / `bespoke`).
- For native: which Trino catalog/schema/table.
- For flex: path (or content hash) of the approved Python module, catalog-level properties (roots, credentials refs, rate limits), and optional `init_catalog` settings. Execution is on demand inside Trino via the flex plugin — **no Core-side `memory` materialization**.
- For stock: which stock connector (`logs`, `csv`, `jsonl`, `syslog`, `http_paginated`, …) and its full per-source parameters (see below).
- For bespoke: which custom connector binary (links to AI-generated Trino plugin), and which stock connector it was templated from (if any).
- Which object types this catalog emits.
- For each object type: which traits the catalog populates, and how (column mappings).
- Proposed links (see Layer 4).
- Safety contract (required filters, max fanout, max time range, etc.).

The configuration is human-readable, version-controlled, and reviewable. AI proposes it; humans approve it before anything reaches Layer 1.

#### What a stock-catalog configuration looks like

Stock connectors are the highest-leverage piece of this layer because they replace per-source code generation with per-source configuration. The shape of the config is what makes them flexible enough to absorb most non-native cases that still fit a known pattern.

For example, the `logs` stock connector — a generalization of `examples/log-connector/` — would expose roughly this surface:

```yaml
type: stock
name: app_logs
connector: logs

source:
  root: /var/log/apps
  path_pattern: "{app}/{date}.log"        # path captures become columns
  recursive: true
  file_glob: "*.log"
  compression: auto                        # gz / zstd / none / auto-by-extension

parser:
  type: regex                              # one of: regex, delimited, json, logfmt, syslog
  pattern: '^(?P<ts>\S+)\s+(?P<level>\w+)\s+(?P<msg>.*)$'
  # OR for type: delimited
  # delimiter: ","
  # quote: '"'
  # column_names: [event_time, level, message]

columns:
  - { name: app,        type: VARCHAR,                       source: path_capture }
  - { name: date,       type: DATE,                          source: path_capture }
  - { name: event_time, type: TIMESTAMP(3) WITH TIME ZONE,   source: parse_capture, capture: ts }
  - { name: level,      type: VARCHAR,                       source: parse_capture }
  - { name: message,    type: VARCHAR,                       source: parse_capture, capture: msg }

partitioning:
  partition_columns: [app, date]           # enables predicate pushdown:
                                           # WHERE date = '2025-04-11' skips all other files

safety_contract:
  require_filter_on:    [date, event_time]
  max_files_per_query:  10000
  max_bytes_per_query:  100GB
```

A few things to notice about this surface:

1. **The `path_pattern` doubles as a layout descriptor and a partition declaration.** Captures from the pattern (`{app}`, `{date}`) become columns, and any column listed in `partition_columns` is pruned at split-enumeration time. This is the same trick Hive's directory-partitioning gives you, with no metastore to manage.
2. **The parser is one of a small enumerated set**, not arbitrary code. AI proposes which mode and the per-mode arguments (a regex, a set of column names, etc.). The space of things AI can get wrong is bounded.
3. **Columns are explicit.** A row's column comes from one of `path_capture`, `parse_capture`, or `literal`. AI proposes the mapping; the humans review whether it's correct.
4. **Safety contract is per-source** and lives in the same file. The values are AI-proposed based on the source's likely cardinality.

The rest of the stock library (`csv`, `jsonl`, `syslog`, `http_paginated`) follows the same pattern: a small set of per-catalog parameters, a parser declaration, an explicit column list with sources, partitioning hints, and a safety contract.

#### When to extend a stock connector vs. go bespoke

If a near-fit stock connector exists but is missing one feature (a new compression format, a new parser mode, a new partitioning style), the right answer is almost always to **extend the stock connector** rather than go bespoke. Stock additions are:

- written in a single language (Java, against the SPI), once
- reviewed by humans
- shipped as a DataPro release
- immediately available to *every* customer with similar data

A bespoke connector, by contrast, is written, reviewed, and maintained per-customer. The first few times something is "almost stock," extending stock pays for itself within two or three deployments.

The decision rule is therefore: bespoke is reserved for shapes that are *fundamentally* incompatible with all existing stock modes (a wire protocol, a binary format, a transactional API). Anything that's "stock + one missing feature" is a stock-extension PR, not a bespoke connector.

### Time-series data sources

Time-series sources are simpler than object sources, in much the same way that time-series query languages are simpler than SQL. There is no four-way object split here — almost all time-series sources fall into a single mode: **native protocol passthrough**.

A time-series source binds DataPro to a TSDB backend (VictoriaMetrics, Prometheus, InfluxDB, Mimir, Cortex, Datadog API, Graphite, etc.) and configures DataPro to issue native queries against it.

#### What a time-series source declares

```yaml
type: timeseries_source
name: prod_metrics
backend:
  protocol: promql
  endpoint: http://victoriametrics.prod.internal:8428
  auth: { ... }

discovery:
  # Catalog of available metrics/labels is fetched lazily on first use,
  # cached in-memory for the lifetime of the DataPro process. No background poller.
  metric_inventory_ttl: 6h    # if a query asks about a metric we haven't seen,
  label_inventory_ttl:  6h    # we re-fetch the catalog inline; otherwise it stays cached.

canonical_mapping:
  # source-specific names → DataPro canonical names
  "node_cpu_seconds_total":   cpu_seconds_total
  "node_memory_MemFree_bytes": memory_free_bytes

label_canonicalization:
  # match labels-on-series with object identities (soft cross-reference)
  - source_label: instance
    target_object_type: Host
    match_strategy: identity_string

safety_contract:
  max_time_range:        7d
  max_resolution:        10s        # reject queries asking for resolution finer than this
  max_series_returned:   10000
  required_label_filter: false      # set true to force a label predicate
```

#### Why time series bypasses Trino

Three reasons make routing time-series queries through Trino a bad idea:

1. **Wrong execution model.** PromQL is fundamentally different from SQL — instant vectors, range vectors, rate functions, recording rules. Translating PromQL into SQL throws away the optimizations TSDBs have spent years building.
2. **Wrong storage shape.** TSDBs store time series in a way (per-series compressed chunks, gorilla-style delta encoding) that is fundamentally faster than row-oriented or columnar OLAP for the access pattern. Trino can read it, but loses orders of magnitude.
3. **Wrong consumer expectations.** Grafana and similar tools expect time-series-native responses — not row sets that need to be re-shaped into a chart. DataPro's time-series API mirrors that, so the natural transport is also time-series-native.

So Layer 3b queries leave Layer 2 as native protocol calls (PromQL/InfluxQL/etc.) and never touch Trino.

#### When non-native equivalents do appear

Two edge cases force a more complex setup:

- **Time-series data living in a non-TSDB backend.** Examples: weather observations sitting in a Postgres table; metrics emitted to Kafka; CSV exports from a vendor's monitoring tool. The right move is usually to **materialize into a TSDB** (typically VictoriaMetrics or InfluxDB, both open-source and embeddable) so the source becomes native. The materialization is conceptually similar to a **one-off ETL** in the object world but the target is a TSDB, not Trino.
- **TSDB without a stable client library.** Rare but real (proprietary vendor APIs, custom in-house TSDBs). DataPro would write a small adapter that speaks the backend's native protocol and exposes an HMS-internal time-series API on top. Conceptually analogous to a **bespoke** integration, but it's a protocol adapter in Core, not a Trino connector.

Both edge cases are deferred past Phase 1.

#### AI's role for time-series sources

Lighter than for object sources but real:

- Discover metrics and labels in the backend; propose canonical names where they're inconsistent (`request_latency_ms` and `req_lat_ms` should probably be the same canonical name).
- Propose label canonicalizations against object identities (the `instance="h-918"` label probably matches `Host/h-918`).
- Propose safety contract values based on label cardinality and the backend's typical retention / resolution.
- For dual-exposure: when registering a TSDB, AI may also propose registering it as an object data source (e.g., raw `MetricSample` objects). Because TSDB volumes are usually too large for naive per-row flex, this path almost always lands in **stock** (if we ship a TSDB-shaped stock connector), **flex** with aggressive split batching and safety contracts, or **bespoke** for maximum performance — never "materialize the whole TSDB into Core per query." Two registrations, one backend.

The catalog-building UI for time series is a separate panel from the object catalog UI: instead of "raw → tabular preview" it shows "raw → time-series chart preview" with a small set of test queries the user can sanity-check.

#### What time-series sources do NOT have

To be explicit, things that exist for object sources but not for time-series sources:

- No object four-category model (mostly all are native; rare cases use a small adapter).
- No object types — only series with labels.
- No traits — labels carry all the metadata.
- No links — relationships are expressed via label-canonicalization to object identities, not first-class.
- No flex-style code generation — connection setup is essentially configuration, not per-source Python.

This is by design. The simplicity is what makes time series fast.

## Layer 3a — Objects and Traits

### What an object is

An **object type** is a *named namespace* with a list of *traits*. That is essentially all it is.

```yaml
type: AppInstance
traits:
  - identity:
      key: composite(namespace, name)
  - temporal:
      timestamp: started_at
```

Object types do **not** have a fixed schema. Different catalogs backing the same object type can return different columns. The schema of a returned object is the union of what its backing catalogs emit, with NULLs where a particular catalog doesn't produce a column.

This is deliberate: it accommodates the messy reality that a `Host` from K8s has different fields than a `Host` from a CMDB, but they're still both `Host`s. It also gracefully handles unstructured data — a `LogLine` has no required identity, just a timestamp and text.

### Traits as the unit of capability

A **trait** is a declarative statement that an object type supports a particular operation. Traits are the only thing that makes an object more than a name.

#### Starter trait set (Phase 1)

Two traits are required to make Phase 1 useful:

**Identity trait.**
- Declares: which column (or combination) is this object's canonical ID.
- Type: namespaced — `AppInstance/prod/checkout-pricing` is not the same as `Application/checkout-pricing`.
- Effect: enables joining and deduplication across catalogs that emit this type.
- Optional: object types may not have identity (e.g. `LogLine` — log entries are not joinable by ID). Without identity, the object is essentially append-only and cross-source merging is impossible.

**Temporal trait.**
- Declares: which column is the timestamp, what format it's in (Unix seconds, ISO-8601, custom strftime), what time zone (or "naive — assume UTC", "naive — assume local", etc.).
- Effect: enables time-bound queries. "All `LogLine` objects between 14:00 and 15:00" works even if the underlying source uses milliseconds-since-epoch as integers.
- Required for any object type that should plot in time-series graphs or correlate with other time-bound objects.

#### Future traits

Captured here as possibilities — not implemented in Phase 1:

- **Linked** — declares this object participates in named relationships (Layer 4 makes this explicit).
- **Measurable** — declares a numeric value column with a unit (`cpu_percent`, `latency_ms`, `bytes_in`). Enables aggregation, plotting.
- **Textual** — declares a primary text body column. Enables search, summarization.
- **Owned** — declares an owner reference (team, user). Enables grouping and access patterns.
- **Located** — declares a region/zone/host. Enables spatial grouping.
- **Versioned** — declares a version/revision column. Enables time travel.

Each future trait is added when a real query pattern requires it, not preemptively.

### Who declares what

| Entity | Decides |
|---|---|
| Object type | Which traits it *can* have (and which are required for it to be useful). |
| DataPro catalog | For each trait declared by an object type it emits, *how* to populate that trait from this specific source. |
| Human reviewer | Whether the catalog's proposed mapping makes sense. |

A catalog that fails to populate a required trait for an object type is rejected by Layer 2 — DataPro will not register a catalog that claims to emit `AppInstance` without telling us how to derive its identity.

### Multi-source backing

The same object type can be backed by multiple catalogs:

```
AppInstance object type
   ├── catalog A: kubernetes_cluster_prod
   │     Identity: namespace + "/" + pod_name
   │     Provides: status, started_at, image, owner
   │
   ├── catalog B: postgres_app_registry
   │     Identity: app_id
   │     Provides: owner, language, repo_url
   │
   └── catalog C: deployment_xml_repo (flex)
         Identity: app_id (from XML root)
         Provides: declared_config, expected_replicas
```

When a query asks for an `AppInstance` by its canonical identity, DataPro:

1. Resolves the canonical identity to whatever each catalog calls it (mapping is part of the catalog config).
2. Issues parallel queries to each catalog that has data for this object.
3. Merges the results into a single object, with conflict detection for fields that differ across sources.

### The schema-divergence problem

A real risk: catalog A names the timestamp column `started_at`; catalog B names it `start_time`; both emit the same object type. When you query "all `AppInstance` objects," the result has both columns, half-empty in each row.

DataPro's response is to push the canonicalization into the catalog config:

- The catalog config declares: "this source's `start_time` field maps to the canonical `started_at`."
- Layer 3 sees only canonical names.
- If a divergence is noticed, the user fixes it via the chat UI: "rename `start_time` to `started_at` in catalog B." AI updates the config; next query is correct.

For unstructured data (logs from different infrastructures) total uniformity isn't realistic — Kubernetes logs and bare-metal logs really do have different metadata. The escape valve is that the canonical schema can be *minimal* (just timestamp + body) and source-specific fields ride as optional extras.

## Layer 3b — Time Series

### What a time series is, in DataPro

A time series is an *unbounded, append-only stream of (timestamp, value, labels) tuples* identified by a metric name plus a set of label key-value pairs. A "time series" is therefore distinct from a "metric": one metric (`cpu_seconds_total`) typically has thousands or millions of distinct logical time series, one per unique label combination (`{host=h-918, mode=user}`, `{host=h-918, mode=system}`, `{host=h-441, mode=user}`, …).

Crucially, **a time series is not an object**. It does not have a primary key, it does not participate in links, it does not have traits. It has a name, labels, and an unbounded stream of points.

### Why time series isn't just objects with the Temporal trait

The seductive but wrong move is to model each data point as an object with the Temporal trait, and call it a day. This breaks down in three places:

1. **Aggregation produces nothing meaningful as objects.** When a query asks for `cpu_seconds_total{host=h-918}` averaged at 5-minute resolution over the last 24 hours, the result is 288 numeric points. Those points do not correspond to anything in the real world — they're a downsampled view. Calling each one a "MetricSample object" is technically expressible but semantically false: there is no entity in the system whose identity is "the average over this 5-minute window". Forcing it into the object model creates fictional entities.

2. **The query shape is fundamentally different.** Object queries are point lookups, fanout traversals, and JOINs. Time-series queries are `(name, label-filter, time-range, resolution, aggregation)` — closer to a continuous function over time than a set of records. Forcing time-series queries through an object-shaped API gives users a worse interface and the runtime worse performance.

3. **The runtime requirement is different.** Object queries can ride on Trino. Time-series queries cannot, for the reasons covered in Layer 2. Even if we modeled them as objects, we'd still need to bypass Trino for the actual execution, and now we'd have a misleading abstraction layered on top.

The right answer is to admit the asymmetry. Both abstractions are first-class. Each has a clean API tailored to its access pattern.

### What a time-series query looks like

```
fetch series:
  metric:    cpu_seconds_total
  labels:    { host: h-918 }
  time:      { from: 2026-05-01T00:00Z, to: 2026-05-02T00:00Z }
  step:      5m
  aggregate: avg
```

Returns:

```
[
  { t: 2026-05-01T00:00Z, value: 0.42 },
  { t: 2026-05-01T00:05Z, value: 0.46 },
  { t: 2026-05-01T00:10Z, value: 0.51 },
  ...
]
```

Or, with multiple matching series:

```
[
  { labels: { host: h-918, mode: user   }, points: [...] },
  { labels: { host: h-918, mode: system }, points: [...] },
]
```

Just one shape, used everywhere. Aggregation, label filtering, time range, and step are required; everything else is optional.

### Dual exposure: same backend, two registrations

The most powerful pattern in Layer 3b is **dual exposure**. A TSDB backend (VictoriaMetrics, in our running example) can be registered twice:

- **As a time-series source** (this layer). Queries that want aggregated, plottable data hit the TSDB's native PromQL endpoint and return time-series-shaped results. Fast, native, the right shape for charts and AI prompts that ask "show me the trend."
- **As an object data source** (Layer 3a, via stock / flex / bespoke as appropriate). Queries that want individual data points as queryable, joinable, identifiable entities expose raw samples as `MetricSample` objects with traits like Temporal and Measurable. Usually slower than the time-series view, but enables individual-point JOINs against other objects (e.g., correlating an outlier latency sample with the deploy that happened seconds before it).

The two views serve different consumers. DataViz typically wants the time-series view for plots and the object view for "click on this anomaly point and tell me which host/app/deploy it relates to." DataMCP needs both: agents asking "what's the latency trend over the last hour?" use the time-series view; agents asking "what's correlated with this specific outlier?" use the object view.

The two registrations share nothing operationally — they're independent catalog configurations against the same backend, with different access patterns and different safety contracts.

### Bridging objects and time series via labels

Time series don't have first-class links. But they do have labels, and label values often *match* object identities — `host=h-918` in a series label corresponds to the `Host` object with identity `h-918`.

DataPro's catalog config for a time-series source can declare these correspondences:

```yaml
label_canonicalization:
  - source_label: host
    target_object_type: Host
    match_strategy: identity_string
  - source_label: app
    target_object_type: AppInstance
    match_strategy: identity_string
```

The runtime uses these to:

1. Resolve label values back to object identities for cross-reference. (When DataViz shows a CPU chart with a label, clicking the label can take you to the object.)
2. Allow object-shaped queries to *include* time series. (`fetch Host h-918, include cpu_seconds_total over last 1h` is valid; the Host fetch goes through Layer 3a, the metric fetch goes through Layer 3b, and the response binds them together.)

This is *not* a link in the formal Layer 4 sense — there's no cardinality, no traversal direction. It's a soft cross-reference: a way for the object world and the time-series world to point at each other without being the same.

### Schema of time-series responses

Time-series responses have a fixed shape, unlike object responses which vary by trait/catalog population. The shape:

```yaml
series:
  - labels:    { metric: cpu_seconds_total, host: h-918, mode: user }
    points:
      - { t: 2026-05-01T00:00Z, value: 0.42 }
      - { t: 2026-05-01T00:05Z, value: 0.46 }
      - ...
    metadata:
      unit:         seconds_per_second
      aggregation:  avg
      resolution:   5m
      provenance:   prod_metrics
```

This rigidity is a feature. It makes time-series responses universally consumable by charting libraries, ML models, and AI prompts.

### What this means for safety contracts

Time-series safety contracts look very different from object contracts:

| Object contract | Time-series contract |
|---|---|
| Required filters (must filter by id, etc.) | Required label predicates (must filter by `host` if querying `cpu_*`) |
| Max fanout per parent | Max series cardinality returned |
| Max time range | Max time range and minimum step (resolution floor) |
| Max traversal depth | N/A |
| Disallow patterns (cross joins, full scans) | Disallow patterns (regex label match without anchor, unbounded ranges) |

The shape of the contract matches the shape of the query language. Adversarial certification (when re-introduced) generates pathological PromQL/InfluxQL queries against the same catalog and tightens the contract until they're rejected.

## Layer 4 — Relationships (Links)

### What a link is

A **link** declares a named, directional, cardinality-typed relationship between two object types, anchored to a specific column on the source object type.

```yaml
link:
  name: RUNS_ON
  from:
    object_type: AppInstance
    column: host_id        # in the AppInstance backing catalog
  to:
    object_type: Host
    matches: identity      # joined against Host's identity
  cardinality: many_to_one
```

### What links enable

1. **Traversal queries.** "Give me all `AppInstance`s and the `Host` each runs on" is a single DataPro query. The user does not write a JOIN; they say "include host."

2. **UI semantics.** DataViz uses cardinality to render correctly: clicking the host link on an `AppInstance` takes you to *one* host (not a list). Clicking the apps link on a `Host` shows you a list.

3. **Schema discovery for AI agents.** DataMCP exposes the link graph to agents — "what objects are related to `AppInstance`?" returns `Host`, `Deployment`, `Team`, etc. with cardinality. Agents can plan multi-hop queries against this map.

4. **Safety analysis.** Cardinality + traversal depth tells DataPro how broad a query is. "Give me all `Host`s, including their `AppInstance`s, including those instances' `LogLine`s" expands by potentially huge factors at each hop. The safety contract uses the link cardinality to estimate fan-out before running the query.

### Two kinds of links

- **Derived links** — declared as field-mapping rules. AI proposes them by inspecting catalog schemas (foreign keys in SQL sources, naming conventions, sample-based pattern matching). Most links are derived.
- **Explicit links** — declared concretely between two specific object instances. Used for relationships that aren't expressible as field mappings (e.g. "this `Application` depends on that `Application`", recorded by hand or by a deployment system). Stored in the link store as edges.

### Why links aren't just SQL FKs

This is the suspicious feeling in the proposal — aren't we reimplementing what SQL primary keys and foreign keys already give you?

Three reasons we *can't* push this all the way down to Trino:

1. **Cross-source joins.** A `Host` in a Postgres catalog and an `AppInstance` in a K8s API catalog cannot be joined by SQL FK because Postgres doesn't know about the K8s data. The relationship has to be expressed at a higher layer.

2. **Stock, flex, and bespoke categories.** When the underlying data is XML, logs-on-disk, or a custom Trino connector, there are no FKs to push down anyway. The relationship has to be declared in DataPro's configuration.

3. **Cardinality and direction matter to the consumer.** SQL FKs are uni-directional and don't carry semantic names. DataPro links carry `RUNS_ON` and `OWNED_BY` and `DEPENDS_ON` because DataMCP and DataViz need them.

Where Trino *can* help: for native catalogs where FKs *do* exist in the source schema, AI can propose derived links by reading `pg_constraint` (for Postgres), Mongo's referential metadata (limited), Iceberg manifests (none), etc. The proposal goes into the link store as a derived link, but it's still a link, not a passthrough.

> **Open question:** does Trino expose any cross-catalog primary/foreign-key concept we could push down to? Reading the docs suggests no, but it would simplify a lot if we missed something. Worth a small spike.

## The Query Surface

The Query Surface is the consumer-facing API of DataPro. DataMCP, DataViz, and any third-party programmatic consumer all speak it. It is *not* SQL — but it has a deterministic, transparent compilation to Trino SQL, and that compilation is part of the contract.

### Why the surface is not raw SQL

DataPro deliberately does not expose SQL — Trino's or anyone else's — to consumers. This is not a developer-experience choice; it is structural. Several DataPro responsibilities make raw SQL unworkable as a consumer API:

1. **Links are resolved by DataPro, not declared in the query.** A consumer says "give me this `Host` and the `AppInstance`s running on it." DataPro looks up the `RUNS_ON` link in the link store, finds the join columns, knows which catalogs back each side, and constructs the SQL. The user never writes `ON Host.identity = AppInstance.host_id` because that pairing is link metadata, not query state.

2. **Routing is DataPro's call, including "don't query at all."** Layer 2 decides which backends to hit, in parallel or serial, with what fanout limits, *and whether the query needs to hit a backend at all*. (A pure identity lookup that's already in DataPro's link store may not need to touch Trino.) Raw SQL exposes none of this and forces the consumer to reason about catalogs and federation manually.

3. **Trait normalization happens after the query.** The same logical field may be `name` in one catalog, `app_name` in another, `metadata.name` in a third. Raw SQL exposes physical column names; the Query Surface exposes traits. Filters and projections are written against traits and rewritten by DataPro into per-catalog column names.

4. **Many SQL features have no semantic place in the object model.** Self-joins, recursive CTEs, window functions, set operations, arbitrary subqueries — powerful in row-oriented analytics, but they don't map onto "select objects, traverse links, return a tree." Allowing them would force DataPro to either silently passthrough every SQL primitive (defeating the abstraction) or partially support some (worse — mysterious failures).

The query surface is therefore a **deliberate subset** of object-shaped operations: object-type selection, identity and trait filters, link traversal, projection, simple aggregation, ordering, limit. Nothing more.

### The compilation is deterministic and visible

Whatever shape the surface syntax takes, its compilation to Trino SQL is **fully deterministic**: the same query against the same catalog configuration always produces the same SQL.

That compiled SQL is **not hidden** from the consumer. Every query response makes the SQL Trino actually executed available — likely as a sidecar field on the response, also surfaced in the Dashboard's debug view. This is part of the API contract, not a development-time convenience. It serves three purposes:

- **Debugging.** When results look wrong, the SQL is the next thing to inspect. Hiding it would create a class of bugs that are unfixable from outside DataPro.
- **Trust.** Operators reviewing AI-built catalogs can verify the realized query path. This is critical for a system that takes AI output to production.
- **Performance investigation.** The compiled SQL exposes whether DataPro chose join pushdown, what fanout it produced, whether a subquery hit one or many backends.

The exact mechanics of "show me the SQL" — always returned vs. on-request, single combined query vs. per-catalog list, included in normal responses or only in a debug mode — is a decision for Phase 1 implementation. The principle is fixed: nothing is hidden.

### Surface syntax: undecided, but constrained

The choice between JSON, an SQL-flavored DSL, a GraphQL-flavored DSL, or some custom shape is open. Whatever it ends up being, it has to satisfy:

- **Programmatically constructable.** DataMCP must be able to assemble queries from natural-language intent without string-templating SQL. A nested data structure (JSON, AST) is natural; an SQL-string is awkward to build and dangerous to compose.
- **Inspectable by humans.** Operators reviewing what DataMCP built must be able to read it without a parser. Pure JSON ASTs are noisy here; some surface that reads like a query helps.
- **Closed under composition.** A trait filter on a linked object (e.g. "include `AppInstance`s where `tier = 'prod'`") must compose without special-casing.
- **Express the four primitives only:** object-type selection, identity/trait filter, link traversal (named), projection. Plus aggregation, ordering, limit. Anything outside this set should not be expressible.

For illustration only — not a commitment to a specific syntax — the example "give me host h-918 and the apps running on it" might compile down from any of these:

A nested-JSON form:

```json
{
  "type": "Host",
  "filter": { "identity": "h-918" },
  "include": [
    { "link": "RUNS_ON_INVERSE", "as": "apps" }
  ]
}
```

An SQL-flavored DSL:

```
SELECT Host
WHERE identity = 'h-918'
INCLUDE RUNS_ON_INVERSE AS apps
```

A GraphQL-flavored DSL:

```
host(identity: "h-918") {
  identity
  traits { ... }
  apps: linked(RUNS_ON_INVERSE) { identity, traits }
}
```

All three express the same query. The choice between them is ergonomic, not semantic. The right answer probably comes from prototyping all three with realistic query workloads from DataMCP and DataViz.

### What the consumer specifies vs. what DataPro derives

A useful mental model for the surface contract:

| The query specifies… | DataPro derives… |
| --- | --- |
| The object type to start from (`Host`). | Which catalogs back that object type. |
| The anchor: identity or trait filter (`identity = 'h-918'`). | Which physical columns to filter on (per-catalog). |
| The link names to traverse (`RUNS_ON_INVERSE`, `EMITS`). | The join columns, cardinality, and SQL `JOIN` shape. |
| Optional trait projections, ordering, limit on the final shape. | Whether traversal hits one backend or fans out. |
| (Nothing about SQL, catalogs, or how data is physically arranged.) | Whether to even issue a backend query, or answer from link-store metadata. |

This division is the core design principle. The consumer expresses *intent in the object world*; DataPro turns it into *execution in the SQL world*.

### The result shape

The query surface returns **nested typed objects**, not row sets.

For "give me host h-918 and all apps running on it," the result is conceptually:

```json
{
  "type": "Host",
  "identity": "h-918",
  "traits": { "name": "host-east-918", "region": "us-east-1", "...": "..." },
  "links": {
    "RUNS_ON_INVERSE": [
      { "type": "AppInstance", "identity": "prod/checkout-pricing", "traits": { "...": "..." } },
      { "type": "AppInstance", "identity": "prod/payments",         "traits": { "...": "..." } }
    ]
  }
}
```

What this is **not**:

- A flat row set with columns like `Host.name | Host.region | AppInstance.name | AppInstance.tier`.
- A pair of separate result sets the consumer has to join on the client.
- A SQL-style row-and-column response of any kind.

DataPro takes Trino's row-set output and reshapes it into the tree above. That reshaping is non-trivial:

- **Deduplication.** The same `AppInstance` reached through two different traversal paths is one object, not two.
- **Trait merging.** When multiple catalogs back the same object, their trait values are unified — most-authoritative wins, or all values returned with provenance, depending on the trait's resolution policy.
- **Tree placement.** Each object lands at the correct point in the nested structure, indexed by the link it was reached through.
- **Cardinality fidelity.** Many-to-one traversals return a single object; many-to-many traversals return arrays. The shape of the response reflects the link cardinality, not the SQL cardinality.

The on-the-wire serialization (JSON, MessagePack, Arrow with a sidecar schema, custom streaming format) is a separate concern, probably consumer-dependent. DataMCP almost certainly wants JSON. DataViz probably wants something Arrow-shaped for streaming large object collections. Both are derivable from the same internal tree representation.

## DataPro Core, AI, and UI

The four conceptual layers of DataPro do not all live in one process. DataPro is deployed as **three components** with distinct responsibilities, distinct lifecycles, and a clean dependency graph: UI → (Core, AI), AI → Core. Nothing depends on UI; nothing depends on AI except UI; Core depends on no other DataPro component.

```
┌─────────────────────────────────────────────────────────────────┐
│  Operator's browser                                             │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  DataPro UI — React SPA (static assets, no backend)       │  │
│  │  (catalog-building, debug console, link editor, …)      │  │
│  └────────────┬───────────────────────────────┬──────────────┘  │
└───────────────│───────────────────────────────│─────────────────┘
                │ AI agent / sandbox /          │ queries, metadata,
                │ LLM-mediated requests         │ config writes
                ▼                               ▼
┌──────────────────────────────┐    ┌──────────────────────────────┐
│  DataPro AI — Flask API      │    │  DataPro Core — Flask API    │
│  (AI plane)                  │    │  (data plane)                │
│                              │    │                              │
```

Core and AI both expose Flask HTTP APIs. UI is purely static (HTML / CSS / JS) — it has no backend of its own. The React SPA is the only thing that calls both APIs; every other consumer (DataMCP, DataViz, third-party programmatic clients) calls Core only. AI itself talks to Core's read endpoints to give agents access to sample data and to run candidate queries during sandboxing — never to the customer's data sources directly.

### DataPro Core — the data plane

**Core implements every conceptual layer in this document.** Layer 1 (the managed Trino deployment), Layer 2 (catalog dispatch; **stock** and **flex** Trino plugins plus native/bespoke catalog registration), Layer 3a (object assembly, trait merging, multi-source unification), Layer 3b (time-series passthrough to TSDBs), Layer 4 (link traversal and the link store), and the Query Surface compiler that turns surface queries into Trino SQL — all of it lives in Core. Nothing in the query hot path executes in DataPro UI.

Concretely, Core owns:

- **The Trino deployment (Layer 1).** Core is responsible for starting, configuring, and monitoring Trino. Catalog `.properties` files, plugin JARs (stock + **flex** framework + any bespoke plugins), and Trino server config are managed by Core. Trino runs as a child process or sidecar container, transparent to consumers.
- **The Layer 2 dispatcher.** When a query arrives, Core decides which catalogs to hit, in what order, with what fan-out limit. **Native, stock, flex, and bespoke** catalogs are all queried **via Trino** — Core compiles surface queries to SQL and submits them to Trino. Flex's Python runs **inside the Trino cluster** (flex plugin + worker subprocess); Core does not execute flex Python and does not materialize flex sources into the `memory` connector (see § How flex works).
- **The Layer 3a/3b runtime.** Object assembly, trait normalization, deduplication, tree placement (Layer 3a). Time-series query routing directly to TSDB native protocols, bypassing Trino (Layer 3b).
- **The Layer 4 link store.** Link declarations, derived-link metadata, explicit link edges. All link-traversal compilation happens here.
- **The Query Surface compiler.** Translates incoming surface queries (whatever shape we settle on) into per-catalog Trino SQL plus per-time-series PromQL/InfluxQL. Returns the compiled SQL alongside results.
- **An internal Postgres database.** Core's own metadata lives here — catalog configs, link declarations, safety contracts, audit logs. This is *not* a customer data source; it is DataPro's bookkeeping store. See "What lives in Core's Postgres" below.
- **A Flask HTTP API — the Core API.** Three endpoint families:
  - **Query endpoints** (`POST /query`, etc.). Accept a query in the surface syntax from § The Query Surface; return a nested-object response plus the compiled SQL.
  - **Metadata endpoints** (`GET /catalogs`, `GET /object-types`, `GET /links`, `GET /safety-contracts/{id}`, …). Pure introspection. Powers any consumer's "what's available?" question.
  - **Configuration write endpoints** (`POST /catalogs`, `PATCH /links/{id}`, `PUT /safety-contracts/{id}`, …). Take fully-validated configuration objects, persist them to Postgres, and reload Trino's catalogs as needed. These are typically authored by AI agents in the UI layer and reviewed by humans before being submitted.

Core has **no LLM dependency.** It does not make outbound API calls to OpenAI, Anthropic, or any other provider. It accepts validated configuration as input and runs deterministically. This is the security boundary — the data plane never talks to a third-party LLM.

#### Single-instance by design

Core runs as **one instance at a time per deployment.** Not two, not a load-balanced fleet. This is an explicit design decision, not a temporary simplification:

- Core does no heavy lifting. It's a thin proxy/coordinator around Trino — the actual query work (federation, execution, joins, aggregation) all happens inside Trino. Core's job is catalog management, dispatch, and result shaping. None of those need horizontal scale.
- Catalog management is a low-throughput operation. Operators register catalogs occasionally; the workload is "a few writes per day per operator," not "thousands of requests per second."
- Trino itself scales horizontally (coordinator + workers). When you outgrow a deployment, you scale Trino, not Core.

Concrete consequences of single-instance:
- No need for `pg_advisory_lock` or other cross-process coordination in the reconciler.
- The 60-second heartbeat reconcile and an in-flight `POST /catalogs` *can* race within a single process; the read-modify-write in `reconcile()` is short and idempotent enough that the worst-case outcome is a transient "catalog already exists" / "catalog not found" error that the next reconcile fixes. No data corruption.
- High availability comes from Postgres + Trino being independently HA, plus Core being fast to restart (it holds no in-memory state that isn't in Postgres).
- If a customer ever genuinely needs two Cores (multi-region active-active, etc.), that's a Phase-N design problem requiring real distributed-systems work — not a "just add a replica" toggle.

If this assumption ever needs to change, the design changes too: catalog operations would need leader election or coordination through Postgres advisory locks, the heartbeat would need to be leader-only, and the reconciler would need to be re-examined for concurrent-safety. Don't add multi-instance support speculatively.

### DataPro AI — the AI plane

**AI implements no conceptual layer either.** It does not execute queries, dispatch to catalogs, or talk to Trino. AI is the home of every LLM-mediated capability and nothing else.

Specifically, AI owns:

- **AI agent orchestration.** Spinning up LangGraph workflows, holding agent state across multi-turn conversations, providing the agent with a tool surface (read source files, sample data via Core's read endpoints, run a test query through Core, validate a regex), and streaming partial outputs back to the SPA.
- **LLM provider integration.** API keys, retries, rate-limiting, cost tracking, prompt versioning. *All* outbound LLM calls go through this service. Core never calls an LLM directly, and the SPA never holds LLM credentials.
- **Sandbox execution of AI-proposed artifacts.** When AI proposes a **flex** Python module, a **stock** YAML config, or (Phase 2+) a **bespoke** plugin, AI runs the candidate in an isolated environment to test it. Test queries against the candidate go through Core (read endpoints only); AI never bypasses Core to query data sources directly. Draft flex code is exercised in the AI sandbox first; approved modules are deployed to the path Trino's flex catalog references.
- **Operator session and auth for the SPA's AI-mediated operations.** Identity, role, and "what is this operator allowed to ask the AI to propose and submit."

AI exposes a Flask HTTP API. The SPA is the primary consumer, but the API is shaped as a real HTTP service so that other clients (a CLI, a CI/CD bot, an external script that wants to programmatically draft a catalog config) can use it without needing the SPA. AI's API is for *proposals and conversations*; Core's API is for *truth and queries*. They are independent — a deployment that wants no AI at all (an air-gapped customer who has already configured everything) can simply not run AI; Core works without it.

When the operator clicks "Submit this catalog" in the SPA, the flow is: SPA → AI (final validation + last-mile sanity checks on the AI-drafted configuration) → Core write endpoint (persist + reload Trino). AI never writes to Core's Postgres directly and never bypasses Core to apply configuration itself — its only job at submission time is to package the validated config and forward it.

### DataPro UI — the presentation plane

**UI is purely a frontend asset.** A React single-page application, served as static HTML/CSS/JS from any web server (a CDN, an Nginx container, S3 + CloudFront — the choice doesn't matter). It has no backend of its own.

UI is where every "human reviews AI's proposal" interaction happens visually:

- The catalog-building view — the three-panel chat layout from § Layer 2, what earlier in this document was called "the Dashboard."
- The object-type editor.
- The link-declaration editor and the link graph visualizer.
- The debug console for compiled SQL.
- The safety-contract editor.
- The audit-log browser.

The SPA is a *thin client*: every piece of state and behavior it shows comes from one of the two backend APIs. It calls **both APIs** depending on what it's doing:

- **Calls Core directly** for: running ad-hoc queries against existing catalogs, fetching object/link/catalog metadata for inspection, viewing audit logs. Anything that doesn't involve an AI agent.
- **Calls AI** for: anything involving an AI agent (proposing a new catalog, suggesting a parser regex, debugging why `read_split` failed), authoring or editing configurations before they're committed to Core, sandbox testing of AI-proposed code.

UI's lack of a backend has real benefits. The SPA can be cached, edge-served, and rolled back independently of any backend. A "DataPro release" is now three independently-deployable artifacts (Core image, AI image, UI bundle) instead of one monolith — which is exactly the kind of decoupling that lets a small team ship reliably.

### What lives in Core's Postgres

A first cut at the schema. This is where v1's vague "metadata store" becomes specific:

| Table | Holds |
| --- | --- |
| `catalogs` | One row per registered data source. Includes category (`native` / `stock` / `flex` / `bespoke`), config blob (typed JSON), version, owner, status. |
| `object_types` | Declared types (`Host`, `AppInstance`, `LogLine`, …) with their trait sets. |
| `object_type_catalogs` | Many-to-many: which catalogs back which object types, with column-mapping JSON. |
| `links` | Link declarations from Layer 4. Direction, cardinality, source/target columns, name + reverse name. |
| `link_edges` | Explicit-link edges (the rare case where links are stored row-by-row, not derivable from joins). |
| `identity_rules` | Per-object-type rules for resolving identity across catalogs. |
| `safety_contracts` | Per-catalog or per-object-type contracts (required filters, max fanout, max time range, …). |
| `query_audit_log` | Every query that hits Core. Includes original surface query, compiled SQL per catalog, row count, latency, consumer ID, fan-out estimate. |
| `config_history` | Append-only log of every configuration change. Who, when, what, AI-proposed-vs-human-edited. |

This Postgres is small (kilobytes-to-megabytes per customer). It is **not on the data path** — Core does not consult it during query execution beyond loading relevant configs into memory at startup and on config-change events. Latency-critical query operations look up in-memory state, not Postgres.

### Why three components rather than two (or one)

1. **Failure isolation.** If AI's agent orchestrator OOMs because someone fed it a 100 MB log file, the data plane keeps serving queries. If the SPA crashes in someone's browser, Core and AI keep running. Each blast radius is contained to one component.
2. **Resource separation.** Agent runtimes are bursty and memory-heavy; the data plane is the opposite — long-lived JVM (Trino) and a small steady-state Flask process. Co-locating them creates pathological scheduling. Static asset serving has yet another profile (essentially free, infinitely scalable).
3. **Deployment flexibility.** Three components mean three orthogonal deployment choices:
   - **Core only.** A customer who has finished configuring their catalogs and wants zero LLM exposure in production runs just Core. AI and UI are turned off.
   - **Core + AI without UI.** A programmatic customer (a CI/CD bot drafting catalog configs against AI's API, or a backend service consuming Core's query API) doesn't need the SPA. UI becomes optional infrastructure.
   - **All three.** The full operator experience.

   None of these are afterthoughts; the three-component split *makes them possible*. A monolith would force the customer into "all or nothing."
4. **Security boundary, sharpened.** The data plane never reaches a third-party LLM. The presentation plane holds no credentials and runs untrusted code (it's a browser SPA). The AI plane is the only side with LLM keys. Each component's threat surface is narrower than a combined service would be.
5. **Independent release cadence.** UI bundles change often (UX iteration). AI's prompts and tool surfaces change often (model upgrades, new catalog categories, new stock connectors). Core changes slowly (it's a runtime; stability matters). Three artifacts means each can ship at its natural rhythm.
6. **Mental-model fit.** v1's "Core/Dashboard" split was always present but vague. This gives it concrete deployment artifacts (three components, two Flask APIs, one bundle of static assets, one Postgres, one Trino). Anyone reading the codebase can immediately tell which side something belongs on.

### Boundary rules

Three rules together fully specify where any new piece of functionality belongs:

1. **If it touches customer data → Core.** The data plane is the only thing with a network path to customer data sources. Nothing else is.
2. **If it requires an LLM → AI.** The AI plane is the only thing with LLM credentials. Nothing else has them.
3. **If it renders → UI.** The presentation plane is the only thing the operator's browser executes. Nothing else does.

A feature that seems to need two of these (e.g. "use AI to debug a slow query") is decomposed: AI proposes the diagnosis, Core runs the diagnostic queries, UI renders the result. Each component does its single job; none of the three crosses a rule.

The narrow exception is sandbox execution of AI-proposed artifacts — **flex** Python module testing, **stock** YAML validation, eventually **bespoke** plugin compile/test. The sandbox lives in DataPro AI (it's testing AI-generated artifacts) and is deliberately walled off from production data sources: it can call Core's read-only endpoints to pull sample data, but it cannot call write endpoints, and it has no direct network path to customer databases. The point of the sandbox is to surface AI-introduced failures *before* code reaches production paths on Trino.

## How a query flows through the layers

Two worked examples — one mostly-object, one with a time-series component — illustrate how the layers cooperate.

### Example A: object query with link traversal

The user asks (via DataMCP or DataViz):

> Give me the `AppInstance` named `checkout-pricing`. Include its `Host`. Include `LogLine`s from this app within the last hour.

Flow:

1. **Layer 4** receives the query. It sees three object types and link traversals.
   - Resolves: `AppInstance → RUNS_ON → Host` (via link from AppInstance.host_id to Host.identity).
   - Resolves: `AppInstance → EMITS → LogLine` (via link from AppInstance.identity to LogLine.app_id).
   - Estimates fanout: 1 AppInstance × 1 Host × N LogLines (where N is bounded by the time filter).
   - Checks safety contract: "LogLines must be filtered by time." ✓ (1-hour window provided).

2. **Layer 3a** receives a sequence of object-fetch requests:
   - Fetch `AppInstance` with identity `prod/checkout-pricing`. Required traits: identity. Optional traits: temporal.
   - Then for the resolved instance, fetch `Host` by identity.
   - Then fetch `LogLine` where `app_id = prod/checkout-pricing` and `timestamp > now()-1h`.

3. **Layer 2** maps each object request to one or more catalogs:
   - `AppInstance/prod/checkout-pricing`: catalogs A (K8s, native), B (Postgres registry, native), C (XML config repo, **flex**). All three are queried **through Trino** in parallel as separate catalogs.
   - For catalog C: Trino scans the `flex_deployment_xml` catalog (name illustrative). The **flex plugin** invokes the registered Python module: `get_splits` enumerates the repo paths / files matching the query's constraints; workers call `read_split` per split to parse `app-configs/checkout-pricing.xml` into rows. No Core-side materialization and no `memory` connector round-trip.
   - `Host/host-east-918`: catalog D (K8s nodes, native). One query.
   - `LogLine`: catalog E (log archive, **stock** — using the `logs` connector with a `path_pattern` of `{app}/{date}.log` and `partition_columns: [app, date]`). One query against the catalog with time + app_id filters from the safety contract; the partition columns let Trino skip every file whose path doesn't match.

4. **Layer 1** executes:
   - Three parallel SQL queries to Trino against catalogs `kubernetes`, `postgresql`, and the flex catalog for C.
   - One SQL query to `host_k8s`.
   - One SQL query to the `logs` stock connector. Trino's planner uses the connector's declared partition columns to enumerate only the files matching `app=checkout-pricing` and `date` within the last hour's window — typically a handful of files even from a large archive.

5. **Results merge upward:**
   - Layer 2 returns rows-per-catalog to Layer 3a.
   - Layer 3a unifies the catalog results into a single `AppInstance` object, applies trait normalization (canonical column names), records field-level provenance.
   - Layer 4 attaches the `Host` and `LogLine`s as nested objects under their links.
   - Result is returned to the consumer.

There is **no step 6 cleanup** for a Core-managed `memory` table — flex reads are query-scoped inside Trino's flex worker; the next query that needs the same XML config re-runs split enumeration and `read_split` under that query's predicates.

### Example B: hybrid object + time-series query

> Give me the `Host` `h-918`. Include `cpu_seconds_total` for it over the last hour at 1-minute resolution.

This query touches both Layer 3a (the object) and Layer 3b (the metric). It is decomposed into independent fetches that share a context (the `Host` identity) and merge in the response.

Flow:

1. **Query parser** (above Layer 4) detects the dual-shape: one object fetch + one time-series fetch. Splits accordingly.

2. **Object branch (3a → 2 → 1):**
   - Layer 3a: fetch `Host` with identity `h-918`. No link traversals needed.
   - Layer 2: route to catalog D (K8s nodes, native).
   - Layer 1: one Trino SQL query.
   - Result: `Host` object.

3. **Time-series branch (3b → 2, bypassing Layer 1):**
   - Layer 3b: fetch series matching `metric=cpu_seconds_total, host=h-918, time=last 1h, step=1m, aggregate=avg`.
   - Layer 2: route to time-series source `prod_metrics` (VictoriaMetrics). Apply safety contract: max range 7d ✓, min step 10s ✓.
   - PromQL emitted: `avg_over_time(cpu_seconds_total{host="h-918"}[1m])` evaluated as instant queries on a 1-minute step grid over the last hour.
   - Result: a single series with 60 points.

4. **Merge:**
   - The two branches return independent payloads. The query parser binds them together: `host` field at top level (the object), `cpu` field at top level (the series).
   - Field-level provenance is preserved on both sides.
   - Result: `{ host: {...}, cpu_seconds_total: { points: [...], labels: {...} } }`.

Notice that **Trino was not involved in the time-series branch** — it went straight to VictoriaMetrics over PromQL. The two branches ran in parallel; the worst-case latency is the slower of the two.

Each layer's behavior is deterministic given its configuration. AI is nowhere in either hot path — it only shows up at setup time when a catalog, link, or canonicalization rule is created/edited.

## Implications for the development plan

Several things shift versus the v1 plan:

1. **Phase 1 must include flex catalogs, not just native.** The "five XML files" case is too core to defer: operators need AI-assisted **Python** that runs under the flex plugin, with the catalog-building UI as the review surface. Stock covers high-volume patterns (logs first); flex covers everything else that isn't native.
2. **DataPro is three components from day one, not one.** Phase 1 ships DataPro Core (Flask + Postgres + managed Trino), DataPro AI (Flask + LangGraph agent runtimes + sandbox + LLM integration), and DataPro UI (React SPA, no backend). The temptation to start with a monolith and "split later" should be resisted: the security boundary (Core never calls LLMs; the SPA never holds credentials; AI never bypasses Core) is the kind of thing that's much harder to introduce after the fact. The three components share an internal network and possibly a Docker Compose / Kubernetes manifest, but they are independently buildable, deployable, and ownable.
3. **The Dashboard view (inside the SPA) is a real product surface, not an afterthought.** The three-panel chat UI is the catalog-building experience. Build it, don't config-file it.
4. **One stock connector ships in Phase 1 (`logs`); the flex framework ships in Phase 1; bespoke is deferred.** The `logs` stock connector — generalized from `examples/log-connector/` — is the right Phase 1 target for volume-heavy plain-text logs (YAML config only). **Flex** ships as the second Trino plugin alongside stock: AI-generated Python for XML / odd files / small APIs without Trino restarts. Other stock connectors (`csv`, `jsonl`, `syslog`, `http_paginated`) are Phase 1.5. **Bespoke** (AI-generated Java SPI from stock templates) is Phase 2+ — by then we have signal on which shapes truly need it.
5. **The link store is necessary for Phase 1.** Even if only derived links are supported initially, the data model has to include them or queries can't traverse.
6. **Safety contracts bind to *catalogs*, not to *objects*.** The safety budget for `LogLine` depends on which catalog is backing it — a stock log archive has totally different cost characteristics from a Postgres-backed `LogLine` table. Per-catalog contracts.
7. **Layer 3b (time series) is part of Phase 1, not later.** A useful Phase 1 must support at least one TSDB backend (probably VictoriaMetrics or Prometheus) end-to-end. The TS source is simpler than object sources to ship — no flex Python, no link store integration on the TS path — but it must exist or the abstraction is incomplete. Dual-exposure (same backend as both object and time-series source) can be deferred.
8. **No background workers in Phase 1 (or anywhere).** Flex and stock execute strictly on demand inside Trino. There is no scheduler, no cron, no batch worker, no cache invalidator. This removes a large amount of infrastructure that v1 implied was needed.

## Open Questions

These are tracked as decisions to make before locking the architecture or shipping Phase 1.

### 1. Are objects necessary as a primitive, or could traits alone do the work?

The user's instinct: "I'm kind of almost considering removing the idea of an object and simply having traits." There's a real argument here — an object type is just a tagged collection of traits, and you could imagine a system where you just declare "this row has Identity + Temporal + Measurable" without ever giving it a type name.

**Argument for keeping objects:** Names give consumers something to query against ("give me all AppInstance objects" is meaningful; "give me everything with Identity + Temporal" is not). Object types are also the natural unit for link declarations and for Dashboard organization.

**Argument against:** Two catalogs emitting differently-shaped "AppInstance" objects effectively make the type meaningless; what matters is the trait set. A trait-only model is more honest.

**Tentative answer:** Keep objects. Names are how humans and AI agents navigate the system; without them, the link layer collapses. But the type is *always weaker than the trait declarations*, and divergence between catalogs is expected and tolerable.

### 2. ~~Adapted vs foreign vs JIT materialization?~~ — **SUPERSEDED: four-way native / stock / flex / bespoke.**

The old **adapted** path (Core runs `fetch`/`transform`, materializes into Trino's `memory` connector) is **removed**. Long-tail, AI-generated catalogs are **flex**: Python runs **inside Trino** via the flex plugin, with streaming splits and optional predicate pushdown — no Core-side materialization tier and no Trino restart for new Python modules.

**Bespoke** remains the escape hatch when Python performance or wire-protocol needs rule out flex. **Stock** remains the escape hatch when the shape matches a shipped Java connector.

The benefit of the hard line is unchanged: **no background materialization jobs**, no cross-query stale cache owned by DataPro. The new trade is operational: flex Python must be **sandboxed and resource-bounded on Trino workers**, not only in DataPro AI's draft sandbox.

### 3. Should `get_splits` and `read_split` stay separate in the flex contract?

Captured above (§ Two stages). Initial bias: **keep separate** for operator mental model and failure attribution. If profiling shows IPC chatter dominates for tiny sources, allow an optional **fused** fast path in the flex ABI.

### 4. How aggressively do we canonicalize column names across catalogs?

For structured types (AppInstance, Host) the answer is "totally" — every catalog maps to canonical names declared on the object type. For semi-structured types (logs from heterogeneous infrastructures) total canonicalization isn't realistic. Where's the line, and how do we represent partial canonicalization without leaking source detail to consumers?

### 5. Does Trino support a cross-catalog primary/foreign key concept we could push down to?

Probably no, but worth confirming with a small spike. If yes, derived links could be partially expressed as Trino metadata and let the planner do more work for free.

### 6. Within-query reuse for flex catalogs

A single SQL query may reference the same flex-backed table multiple times (self-join, repeated subquery). Does Trino's planner **deduplicate scan nodes** enough that Python isn't invoked redundantly? If not, does the flex plugin need **query-scoped memoization** of split descriptors or row batches?

To confirm during implementation: trace real plans for duplicated flex scans; add memoization in the flex plugin only if the planner doesn't already fold identical scans.

### 7. Sandboxing flex Python (two places)

There are **two** distinct trust boundaries:

1. **DataPro AI sandbox** — runs *draft* flex modules while the operator is iterating. Same isolation story as today (subprocess / container, no write endpoints to Core, sampled data only).
2. **Trino worker** — runs *approved* flex modules on the hot path with access to real credentials and real data volumes. Needs **harder** caps: CPU, memory, wall time per split, syscall filtering, optional network egress allowlists.

The open question is how much of (2) is **OS primitives on the worker** vs **co-process supervisor inside the flex plugin** vs **"flex only on dedicated worker pool"** scheduling in Kubernetes.

### 8. Are we re-implementing SQL concepts at a higher layer?

The user noticed: identity ≈ primary key, link ≈ foreign key. We're doing it *across* sources Trino can't natively unify, with cardinality + name + safety annotations Trino doesn't carry. So it's not redundant — but the suspicion is healthy. Worth checking periodically that we're adding meaningful semantics, not paperwork.

### 9. ~~What does a catalog update do to materialized data?~~ — **MOOT for flex (no Core `memory` tier).**

Updating a flex module changes what the next Trino scan does — there is no separate materialized table in Core to reconcile. **Operational detail:** does Trino need a **catalog reload** or **worker subprocess restart** to pick up a replaced Python file on disk, or does Core signal the flex plugin to hot-reload? Decide per deployment (NFS vs immutable image vs ConfigMap volume).

Stock and bespoke still have their own upgrade stories when the **Java** plugin version changes (image rollout).

### 10. Does the object model need an explicit "no identity / append-only" mode?

`LogLine` is the canonical example: no joinable identity, only temporal. The current model handles this by making the Identity trait optional. But that creates a quietly-different class of object whose semantics (no merge across catalogs, no link target) are subtly different. Worth deciding whether to make this explicit in the type system rather than implicit in trait absence.

### 11. Dual exposure: one config or two?

A backend that is both a time-series source and an object source — should it be registered as one config with two sections, or as two completely independent configs? Argument for one: the auth/connection-detail share is real. Argument for two: every other aspect (safety contract, query path, AI build process) is independent, and conflating them invites confusion. Tentative answer: two independent configs that share an auth credential reference. Confirm during implementation.

### 12. How are label-to-identity bridges expressed and validated?

The `label_canonicalization` block in time-series source config makes claims like "this `host` label value matches `Host/<value>` identities." That's a strong claim with a bunch of edge cases — missing labels, label values that don't match any object, label values that match wrong object types. How is this validated at registration time? Does the AI sample-check it? Does the Dashboard surface mismatches the operator can correct?

### 13. Time-series query language

We need a small-but-real DataPro-side query shape for Layer 3b. Three options:
- **Pass-through to PromQL/InfluxQL.** Maximum power, but ties consumers to the underlying TSDB's dialect. Loses the abstraction.
- **Canonical query shape (`metric + labels + range + step + aggregation`)** that compiles to the underlying TSDB's dialect. Good for 95% of queries, restrictive for the long tail.
- **Both: canonical for routine cases, raw passthrough as an escape hatch.** Probably the right answer, mirrors how DataPro's object queries should compile to SQL but sometimes pass through.

Decide which we're shipping first.

### 14a. Query surface syntax

JSON nested form, SQL-flavored DSL, GraphQL-flavored DSL, or custom? The semantic model is fixed (object selection + filter + link traversal + projection); the choice is about ergonomics and how AI agents in DataMCP construct and inspect queries. Decision likely comes from prototyping all three against realistic workloads.

### 14b. Result shape and on-the-wire serialization

Nested typed objects is the conceptual model. The wire format almost certainly varies by consumer: JSON for DataMCP, something Arrow-shaped or streaming for DataViz, possibly MessagePack for low-overhead programmatic use. The internal tree representation must be expressible in all of them. Decide the canonical first format (almost certainly JSON) and what the conversion to the others looks like.

### 14c. How is compiled SQL surfaced to the consumer?

Always returned in every response (cheap, but bulky)? On request via a flag (cleaner, but two-call workflow)? Visible only in the Dashboard's debug view (cleanest API, but invisible to programmatic consumers debugging in production)? The principle "compiled SQL is not hidden" is fixed; the mechanics of how it's delivered are open.

### 14d. Stock-catalog configuration DSL

The illustrative `logs` config in Layer 2 is YAML with a free-form "anything goes" structure. The real shape needs to be:

- **Strongly typed** — config errors should fail at registration time with helpful messages, not at first-query time.
- **Self-documenting** — operators reviewing AI-proposed config should be able to see what each field means and what its valid range is.
- **Forward-compatible** — adding a new parser mode or a new partition style to a stock connector should not break existing configs.
- **Code-renderable** — DataMCP should be able to construct config programmatically as easily as a human can write it in YAML.

Candidate shapes: hand-rolled YAML schema with JSON Schema validation; Pydantic / dataclass-based with YAML serialization; a custom typed DSL. Decide before the stock library grows beyond `logs`.

### 14e. Stock-connector versioning and migration

Stock connectors will gain features (new parser modes, new partition styles, fixed bugs). Customer configs reference specific stock connectors by name. When a stock connector ships v2 with a backward-incompatible config change, what happens to existing v1 configs? Options: pin connector version per config, support both versions with a migration path, force migration on upgrade. The right answer probably depends on how often we expect breaking changes (target: rarely).

### 15. Sandbox isolation for AI-proposed code in DataPro AI **and** flex on Trino

DataPro AI's sandbox runs draft **flex** Python, **stock** YAML validation, and (Phase 2+) **bespoke** compile/test. Trino workers run **approved** flex Python under stricter caps (see §7). What's the right isolation primitive for each — subprocess + `seccomp`, gVisor, dedicated node pool, Firecracker? Phase 1 might accept subprocess + restrictions for (1) and a **dedicated flex worker pool** for (2) until harder isolation ships.

### 16. How does Core's Postgres relate to schema migrations?

Core's internal Postgres holds the source of truth for catalogs, links, traits, etc. When DataPro itself ships a new release that needs to add a column (e.g., a new safety-contract field), how is that migrated? Standard tools (Alembic for SQLAlchemy, Flyway, Liquibase) are options. Decide before Phase 1 ships and a customer accumulates state we have to migrate.

### 17. Does AI ever read from Core's Postgres directly?

The natural answer is no — AI talks to Core's HTTP API, never to its database. But there are pragmatic exceptions: AI agents reasoning about the link graph or the catalog inventory could be much faster against a read replica than through paginated API calls, and audit-log inspection in the SPA might benefit similarly. Decide whether AI gets a read-only Postgres role, or whether everything stays behind the HTTP boundary even at performance cost. (The SPA does not get any direct DB access regardless — it only ever talks to Core's and AI's HTTP APIs.)

### 18. What about cross-source time-series JOINs?

Two TSDB backends (e.g., a VictoriaMetrics + an InfluxDB), each holding their own metrics. A user wants to plot one against the other. Trino can't help here. Options:
- DataPro fetches both, joins in process. Memory-bounded, slow for big windows.
- DataPro picks a primary backend and pulls the secondary's data into it on demand.
- Reject as out of scope for Phase 1.

Probably "reject for Phase 1" is right, but worth deciding rather than discovering.

### 19. Flex framework: dependencies, hot reload, and IPC choice

Open design choices for the flex plugin: **fixed Python environment** baked into the Trino image vs **per-catalog venv**; how **third-party packages** are approved (lockfile review vs deny-by-default); whether **module hot reload** is supported without worker restart; and whether Java↔Python uses **Arrow Flight**, plain gRPC, or stdin/stdout framing. These affect security review, cold-start latency, and operator ergonomics.

- **"Time series as a top-level abstraction alongside Objects"** — *retained and reinforced*. v2 sharpens this into Layer 3b, with explicit non-goal of forcing time series into the object model. Aggregated/sampled time series do not produce meaningful objects, so the distinction is preserved.

The three components are precise: DataPro Core (data plane, Flask + Postgres + managed Trino, all four conceptual layers, no LLM dependency); DataPro AI (AI plane, Flask + LangGraph agents + sandbox + all LLM calls, no direct path to customer data); DataPro UI (presentation plane, React SPA served as static assets, no backend). - **"VictoriaMetrics as objects via Trino, dual-exposed alongside native time-series connector"** — *retained as the dual-exposure pattern in Layer 3b*, but cleaned up: object exposure goes through Layer 3a's **stock / flex / bespoke** categories (rather than being a built-in Trino-side feature), while time-series exposure goes through Layer 3b's native protocol passthrough. Two independent catalog configs against the same backend.
- **"AI runs the query language at runtime"** — *retained* (still false; runtime is deterministic), now structurally obvious from the layer separation.
- **"Adversarial performance certification"** — *retained in spirit* (per-catalog safety contracts on both 3a and 3b sides) but the certification flow itself isn't redesigned in this revision; carry over from v1.
- **Adapted (Core JIT → `memory` connector) and the old native/adapted/foreign split** — *superseded*: AI-generated Python for the long tail runs under the **flex** Trino plugin (streaming splits); high-volume known shapes use **stock** (Java); rare hot-path cases use **bespoke**.
